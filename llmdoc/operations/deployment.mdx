# Deployment and Runtime Modes

## Choose the correct topology

Local development, generic self-hosting, and the current production server are different workflows:

- `pnpm local` starts only the data services in Docker, applies migrations, and runs Web, collection, and analysis as source development processes.
- Generic self-host uses the base Compose topology and published or locally built production images, normally exposing Web only on loopback for a host Nginx proxy.
- The current production server merges the base, server, and host override Compose files, builds China-network Dockerfile variants from source, removes the direct Web host port, and relies on an external Docker edge proxy for HTTPS.

Do not infer one mode's port, proxy, or build behavior from another.

## Production branch policy

Production deploys only `main`. Every code change must be reviewed as appropriate, committed, merged into local `main`, and pushed to `origin/main` before the server is updated. Never develop, commit, merge, or resolve conflicts in the server worktree.

Before deployment, the server must have no tracked changes, must switch to `main`, and must fast-forward to exactly `origin/main`. Do not create or check out feature, snapshot, hotfix, or ad-hoc deployment branches on the server. After safe integration into `main`, obsolete server-local branches should be removed so branch state cannot be mistaken for deployed state.

The current deployment script still exposes a branch override. That option conflicts with this policy and must not be used. Removing or enforcing it is a source-code task, not a documentation shortcut.

## Pre-deployment gates

1. Confirm required tests and type checks passed before pushing `main`.
2. Record the previous production revision and image identity for recovery.
3. Verify the server's `main`, `origin/main`, and intended release revision agree.
4. Reject tracked dirty state. Preserve unrelated untracked operational files unless they block the build context.
5. Confirm free disk space, the external edge network, persistent volumes, and the host storage path before building.
6. Resolve which services changed; avoid rebuilding or restarting unrelated stateful services.

## Safe deployment sequence

1. Merge Compose files in this order: base, server variant, then the host resource override.
2. Build only affected images when service contracts permit it.
3. Run the one-shot PostgreSQL migration and required ClickHouse schema synchronization before replacing Web.
4. Stop on any migration failure; do not replace a healthy application with an image that expects an unapplied schema.
5. Recreate only affected services unless a dependency contract requires more. Do not restart databases or browser workers for documentation-only or Web-only changes.
6. Wait for health transitions instead of treating container creation as success.
7. Test the real HTTPS edge path plus `/api/health`; a `200` login page alone does not prove the databases or queue are healthy.

## Website edge host isolation

The independent public website uses an external Nginx container, separate from the application Compose project. `scripts/deploy-website.sh` applies the host guard before publishing static content. The repository owns the rejecting defaults and their guarded migration; the existing named-host routes and certificate lifecycle remain external operational dependencies.

DNS pointing at this server does not authorize a domain to serve the website. The website must never be the fallback for an unmatched host, and unknown HTTP hosts must not be redirected using their supplied `Host` value. `scripts/website-edge-default.conf` provides the IPv4 and IPv6 rejecting defaults: unknown HTTP hosts receive 404, unknown TLS SNI names fail the handshake, and a request with valid site SNI but an unknown HTTP Host also receives 404. A canonical link in page HTML does not replace this routing boundary.

Keep the existing `geok.cloud`, `www.geok.cloud`, and `tool.geok.cloud` routes, redirects, and ACME challenge locations intact. `scripts/restrict-website-hosts.sh` checks the main-only clean-checkout contract, the expected configuration bind mount, and the inspected listener/named-host topology before migrating it. Unexpected topology or a modified managed prefix requires inspection; do not weaken those guards merely to make deployment pass. Once installed, repeated runs verify the existing restriction without rewriting or reloading it.

The production configuration is `/opt/jianke-sites/nginx.conf`, file-bind-mounted into `jianke-sites-web`. Test the candidate with the running edge image, network, mounts, and certificates before changing the live file. Back up the prior configuration under `/opt/jianke-sites/edge-backups/`, then write in place, run `nginx -t`, and reload. **Preserve the file inode on both apply and restore**: replacing the host file with a rename can leave the container reading the old bind-mounted inode. Certificate private keys are not part of the repository or these configuration backups.

After a write, a failed configuration test, reload, or routing verification triggers restoration of the previous file and another test/reload. This rollback covers only this configuration update; it does not roll back application containers, database migrations, or subsequent static publishing. If restoration itself fails, use the reported backup path for recovery and recheck the live routes. Restoring a pre-guard configuration can reintroduce foreign-domain access, so a rollback is not evidence that host isolation is fixed.

Verification must exercise both allowed and rejected traffic: the homepage, case page, sitemap, `www` redirect, tool route, named-host HTTP redirects, an unknown HTTP Host, unknown TLS SNI, and the valid-SNI/unknown-Host combination. `bash scripts/test-website-edge.sh` reproduces the original fall-through and checks the fix in disposable Nginx, including ACME preservation, idempotence, and refusal of an unexpected topology. The `--prepare INPUT OUTPUT` mode generates a candidate without touching production; it does not replace live verification.

When direct server access is unavailable, the Deploy workflow's `inspect-website-edge` operation reads container mounts and selected routing directives through the existing deployment credentials without applying changes. Keep this diagnostic operation read-only. After a repair, verify the public origin and a rejected host before requesting search-engine recrawling; accepting that request is not confirmation that search results have already updated.

## Verification and handoff

Success requires all of the following:

- server branch is `main`, and HEAD equals `origin/main`;
- migration exited successfully;
- Web reports healthy and `/api/health` returns success;
- collection and analysis containers are running as expected for the change;
- the externally reachable HTTPS route serves the intended application;
- logs show no new fatal, uncaught, repeated restart, or dependency failures.

Report the deployed revision, affected services, verification results, and any check not performed. A documentation-only change should be pushed to `main` but does not require application container deployment.

## Recovery boundary

Container recreation is recoverable; volume deletion is not. If a new image fails, keep data services and volumes intact and restore the previous known revision by making `main` represent the intended rollback, then redeploy from `main`. Do not leave the server checked out at a detached commit or rollback branch.

Application containers and database migrations have no general automatic rollback or pre-deploy data backup. The website edge configuration has the narrowly scoped backup/rollback flow above, and static website publication keeps its own release backup. Neither substitutes for a database or host-storage backup, so stop before destructive recovery and obtain an explicit backup/rollback decision. Never use `docker compose down -v` as routine recovery.

The external production edge proxy and certificate renewal remain outside this Compose project. The repository-managed host guard owns only rejecting defaults and their safe installation, not the entire external proxy or certificate-renewal configuration.
